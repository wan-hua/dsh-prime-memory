1

启动 · 登录 · 账号接入

先有账号，才有人替你听消息

  • start.sh 检查单实例 / 端口 / venv，交给 uvicorn；systemd 负责常驻。
  • FastAPI 打开后台，SQLite 初始化并加载面板保存的配置。
  • 扫码登录写入 Cookie，WorkerManager 为每个启用账号启动 Worker。
  • Worker 建 WebSocket：心跳 → /reg → ackDiff，然后启动轮询任务。
2

配置 · 规则与自动化

规则决定“这一单发什么”，开关决定“要不要自动做”

  • 发货规则按商品匹配：2018K / MiniDaily / 本地卡池 / 固定文案。
  • 2018K 规则绑定实例，时长支持固定、SKU 档位、按金额换算，0 表示永久。
  • 自动回复独立配置：商品回复 / 关键词回复，支持冷却与每会话一次。
  • 订单自动化：领取小红花、求花、提醒收货、自动好评。
3

消息入口 · 解析与去重

推送和拉取最终都汇到同一个处理入口

  • WebSocket 推送进入收帧循环；会话轮询按固定间隔补齐正文。
  • 解析 msgpack/base64 卡片，提取 chat_id、买家、商品、订单号。
  • 先查 seen_messages，同一 messageId 只处理一次。
  • 补买家真名 → 写 messages 流水 → 标记 chat / trade。
  • 旧会话保护：最后消息超过 1 天，整段忽略；只处理新消息。
4

分流 · 自动回复 / 社交 / 发货

系统交易消息不回“在的”，真人消息才进入自动回复

系统 / 交易消息

关闭自动回复；按内容触发领取小红花、提醒收货、求花、好评。

真人聊天

商品 / 关键词规则匹配；冷却与每会话一次；付款文本还要核实订单。

  • 付款卡片或核实过的付款文本进入发货决策；订单轮询同样进入。
  • 已发货、冷却中、无规则、鉴权失败：跳过并记录原因。
5

发货决策 · 按规则准备内容

先判断能不能发，再决定发什么

2018K查金额 → 算天数 → 建卡
MiniDaily生成一次性邀请链接
本地卡池按商品出库并锁定
固定文案变量渲染后直接发送
  • 上游失败：upstream_failed；MiniDaily 失败：invite_failed。
  • 本地卡池出库即锁定，发送失败会退回库存。
6

确认发货 → 发送卡密

关键顺序：先确认，成功后才发送；失败绝不发卡

SUCCESS / 已发货

调用 confirm_shipping 成功，或返回 ORDER_ALREADY_DELIVERY；发送卡密/文案，记 delivered。

ORDER_STATUS_ERROR / 其他失败

不发送；尝试撤销 2018K 卡密，记 confirm_failed；删卡失败则把卡密 ID 写进详情。

  • 发送失败：send_failed，回滚卡密并记录；不会误标为已发货。
  • 发送成功：mark_delivered + 写 outgoing 消息流水。
7

记录 · 面板 · 可观测

所有结果都能在后台追溯

  • 订单状态：delivered / confirm_failed / send_failed / upstream_failed / invite_failed。
  • 消息流水、发货记录、账号连接状态、规则与卡密池都在面板查看。
  • 2018K 健康检查只在启动、保存配置、手动点击时执行，不做定时轮询。

社交自动化（事件驱动）

  • 买家送小红花 → 自动领取
  • 已发货 → 提醒收货 + 求花
  • 确认收货 → 求花 + 好评
  • 按 order_actions 去重
  • 提醒收货每日一次

订单状态

delivered 已发货 confirm_failed 确认失败 send_failed 发送失败 upstream_failed 建卡失败 invite_failed 邀请失败 blocked 鉴权拦截

关键原则

  • 系统交易消息不触发自动回复
  • 旧会话超过 1 天不处理
  • 先确认发货，再发送卡密
  • 失败可回滚，状态终态化
  • 推送 + 轮询双通道互补
